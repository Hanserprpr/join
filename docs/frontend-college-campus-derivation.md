# 按学院自动分配校区

学生的校区不再依赖前端填写，改为服务端按学院从学院专业字典推导。
本次为兼容性增量：URL、请求体、响应字段和权限都没有变化。

## 学院专业列表接口的返回不变

`GET /api/college-majors` 的返回结构、学院键、每个学院的专业数组都和之前一致：

```json
{"文学院": ["汉语言文学"], "法学院": ["法学"]}
```

校区只存在于 Nacos 配置里，加载时就被展平掉，不进这个响应。**唯一的差别是学院键的顺序**：
配置改成校区分组后，展平出来的学院按校区聚在一起，而不是原来的文→理→工→医。
JSON object 的键序没有契约意义，按 map 解析的客户端不受影响；如果前端是按返回顺序渲染学院下拉框，显示顺序会变。

## 校区字段的取值

**校区枚举没有变化，仍然是原来六个济南校区。** 接口不会返回任何前端没见过的取值，
按严格枚举解析 `campus` 的客户端（包括移动端）不需要任何改动。

变化只在于 `campus` 之前几乎恒为 null，现在会被自动填上，影响
`GET /api/user/profile`、`GET /api/auth/me`、报名列表和报名详情。
对前端来说是“本来空的字段现在有值了”，仍然要保留 null 的显示分支：
青岛、威海等济南以外的学院没有对应校区，它们的学生 `campus` 继续为 null。

`PUT /api/user/profile` 仍然接受 `campus` 字段，老客户端继续传不会报错，但它不再是权威值：
字典能按学院推导出校区时以推导结果为准，只有字典没给出该学院校区时才采信请求里的值。

## Nacos 配置格式

推荐改成校区 → 学院 → 专业三层：

```json
{
  "中心校区": {"文学院": ["汉语言文学"]},
  "青岛校区": {"法学院": ["法学"]}
}
```

济南六个校区的键用中文名或枚举名都可以。`"青岛校区"`、`"威海校区"` 也是合法分组，
只是校区枚举没有对应取值：这些学院照常出现在学院专业列表里、学生能正常填报，
但推不出校区，`campus` 保持 null。除此之外的键一律拒绝，拼错的校区名不会被当成“没有校区”放过。

校区名写错、某个校区下没有学院、同一学院出现在两个校区，都会导致整份配置被拒绝并保留上一份快照
（沿用原有的 fail-closed 行为），Nacos 控制台的推送不会生效，只在日志里可见。

老的学院 → 专业两层格式继续支持，此时学院没有校区归属，`campus` 保持原来的行为（采信请求）。
两种格式长期共存，**配置可以随时回滚而不必发版**。

## 上线顺序

1. 先发后端。此时 Nacos 里还是老格式，行为与上线前完全一致。
2. 再在 Nacos 控制台把配置改成校区分组格式，推送即生效，不用重启。

顺序不能反：新格式先推、老代码解析失败会静默保留旧快照，期间重启则退回类路径兜底字典。

## 尚未处理

存量用户的 `campus` 仍为 null，只有在该用户下次更新个人资料时才会被补齐。
需要全量回填时另行执行，按学院分组：

```sql
UPDATE user SET campus = 'SOFTWARE_PARK'
WHERE campus IS NULL AND college IN ('软件学院', '集成电路学院');
```
